# AVENLOCK 4.0 — Approved onboarding rollout

**Status:** source changes and automated regressions checked locally; no production deployment, GitHub push, real Brevo email test, or live Supabase integration test has been performed in this package.

## What changed

- After verified cloud-account sign-in, an account with **no cloud vaults and no unsynced encrypted local vault recovery** enters the new privacy-acknowledgement screen, then a 3-step cloud-vault tour, then the existing secure vault-creation form in its approved premium layout.
- A full 14-section privacy notice is available in the onboarding screen and from the account-creation screen. The **current policy version** is `2026-11-18-v1`.
- Acknowledgement is stored in the `public.privacy_consents` table for the authenticated user's Supabase ID, with timestamp generated by PostgreSQL. Row-level security restricts users to their own records. On a database or network failure, a new user cannot proceed past the acknowledgement.
- A successful Forgot Password request now opens a separate **Check your inbox** screen. Existing Supabase recovery-link routing, new-password form, and sign-out behavior remain unchanged. The screen intentionally does not confirm whether an email address has an account.
- The top-left logo now opens the vault overview when unlocked, or the appropriate home/chooser/onboarding screen when locked. Back navigation was added to the applicable authenticated workspace and onboarding pages; no browser-history-only back actions.
- Input placeholder text, repeated marketing copy, and several presentation-only strings were removed or shortened. Accessible field labels, functional notices, privacy disclosures, password-recovery notices, and error guidance remain intact.
- The **previous master-password warning** is included. No vault encryption algorithms, KDF parameters, ciphertext formats, backup formats, deletion logic, cloud-sync policies, or account-authentication credentials were changed.

7. Perform a **real staging end-to-end test** before using the changes with sensitive data:

## Privacy policy editorial review

The 14-section policy is a **draft based on implementation and named infrastructure** (GitHub Pages, Supabase, Brevo). It is *not a legal compliance certification*. Before offering the app to the public, the operator should check its precise legal identity and privacy contact, user eligibility, applicable law, cross-border transfer disclosures, provider-specific data retention, regulatory rights, and whether an additional legal basis/notice is required. Update the policy and its version/migration if that review changes the notice. Do not state that privacy consent is optional while making cloud-account data processing essential to the service.

## Rollback

If the new UI fails before anyone uses it, restore the prior GitHub repository commit and redeploy. Do **not** delete user vaults or their encrypted backups. The new privacy consent table is independent of all vault tables; it can remain in place during a UI rollback. If users already accepted its policy version, retain their acknowledgement records; do not silently erase legal/audit records.
